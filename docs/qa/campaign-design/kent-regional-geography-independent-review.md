## Findings

- **Modern controls and attribution are internally consistent.** The three features in `docs/research/odyssey-research/geography/kent-modern-place-controls.geojson` are OSM nodes 29038127/Reculver, 9827276975/Richborough, and 17916174/Canterbury. In each case GeoJSON order `[longitude, latitude]` exactly matches the corresponding provenance `[record.lon, record.lat]` and the candidate landmark. The candidate repeats the same three IDs, names, and coordinates. GeoJSON and provenance both identify OpenStreetMap contributors and ODbL 1.0; the response record also advertises ODbL. This supports use as current place-label orientation controls with attribution/license preserved, not as historical positions.
- **Two of three recorded raw API hashes are not reproducible from a fresh response, although the node data still matches.** The local GeoJSON SHA-256 is `f1d5bcae3325bad14800468c6b6ac0393536e6fccf5bc742562fbfd3e922934f`, matching provenance; its byte count is 2,253, also matching. Provenance records raw-response hashes for all three node URLs. Fresh GETs on 2026-10-25 reproduced the Richborough raw response hash exactly. Reculver and Canterbury returned the same ID, name, coordinates, version/timestamp and tags, but different full-response hashes. The live API exposes an instance-specific top-level `generator` value, which can vary across requests; without the original full response bytes, the exact reason for the two mismatches cannot be proven. The local provenance retains only each `elements[0]` record, not the original full response bytes or top-level metadata, so those two historic raw hashes cannot be independently reconstructed from the committed evidence. Keep this as a provenance reproducibility limitation; it does not falsify the node coordinates or local artifact hash.
- **The 400-tile controls reproduce the existing helper.** `tools/design/geography.py::tile_point` maps all three candidate landmark coordinates against `profile.bbox=[1.04,51.25,1.45,51.41]` at size 400 to the exact stored tiles: Reculver `[158.52,131.74]`, Richborough `[269.22,247.52]`, Canterbury `[56.35,268.99]`. The helper uses north-up WGS84, cosine-corrected longitude and a square span padded by factor 1.12. The candidate labels its bbox an architect-selected viewing frame, stores derived `outerCellExtent`/`pointExtent`, and explicitly says it is not a published ancient extent. Neither the bbox nor those controls encode a landfall, shoreline, crossing, objective, or route.
- **The source cautions match the cited material.** Historic England, *Isle of Thanet Landscape Mapping Project* (Research Report 11/2025), printed pp. 4–5 describes the chalk ridge/scarp, plateau and dry valleys; printed p. 124 says the exact Augustine landing location is unknown and reports the Richborough identification as a later Thorne tradition. The candidate and brief preserve those distinctions and do not use the report-area NGR as an event point. The English Heritage visitor history gives 597 arrival, a land grant east of Canterbury and probable 598 abbey foundation; the candidate distinguishes the mission from later abbey fabric and excludes the developed medieval precinct from the 597 map. These sources do not establish an exact arrival route or a 597 coast/water mask.

The arc's Gregory VI.51 note says it supports an underway mission/contact but does not establish the original dispatch date or precise first arrival; the brief states the same limit.

Checks were limited to source-file inspection, three API GETs, local hash/coordinate comparisons, the existing `tile_point` helper and targeted registry/count/link checks. No project test suite, renderer, scenario validator, game, historical approval, or production gate was run. The candidate still needs independent resolution of dated shoreline/channel evidence and final activity-map geography before canonical promotion or gameplay design.
